## 二、机器码生成策略

### 2.1 采集维度（多因子组合）

采集 4 类硬件标识，每类取一个稳定值：

| 维度 | Windows 采集方式 | 稳定性 |
|------|-----------------|:------:|
| 主板序列号 | `wmic baseboard get serialnumber` | ★★★ 极高 |
| CPU ID | `wmic cpu get processorid` | ★★★ 极高 |
| 系统盘序列号 | `wmic diskdrive where "Index=0" get serialnumber` | ★★☆ 较高 |
| 主网卡 MAC | `os.networkInterfaces()` 取第一个非回环 MAC | ★★☆ 中等 |

### 2.2 组合方式

每个维度独立 SHA256，取结果前 8 位作为该维度的「指纹」：

```
fingerprint = SHA256(维度原始值).slice(0, 8)
```

4 个指纹用 `|` 拼接后再做一次 SHA256，得到完整机器码哈希，再用 Base32 编码（每 4 位加 `-` 分隔），最终展示给用户的格式：

```
A3F7-K9M2-XB5Q-W8N1-VC4R
```

### 2.3 模糊匹配（核心设计）

授权码内包含 4 个独立指纹哈希。验证时要求**至少 3/4 维度匹配**才算同一台机器。这样用户更换网卡、加装硬盘等单一硬件变更不会导致授权失效。

## 三、密码学方案

### 3.1 算法选择：Ed25519

| 对比 | 对称加密 (AES) | 非对称签名 (Ed25519) |
|------|:---:|:---:|
| 密钥分布 | 密钥嵌入应用 → 逆向可伪造 | 公钥嵌入应用（只能验签），私钥仅开发者持有 |
| 安全性 | ❌ 不安全 | ✅ 安全 |
| 签名长度 | — | 64 字节 |
| 依赖 | — | Node.js 内置 `crypto` 模块 |

### 3.2 授权码数据结构

```
授权码 = Base64( payloadJSON + "." + Ed25519签名(payloadJSON) )
```

载荷（payload）JSON 结构：

```json
{
  "v": 1,                              // 协议版本号
  "mid": "A3F7-K9M2-XB5Q-W8N1-VC4R",   // 机器码（展示用）
  "fps": [                             // 4 个维度的独立指纹
    "a3f7k9m2",
    "xb5qw8n1",
    "vc4r...",
    "9m2xb..."
  ],
  "exp": 1735689600,                   // 过期时间戳（可选，0=永久）
  "tier": "pro",                       // 授权级别（可选：basic/pro/enterprise）
  "iat": 1719705600,                   // 签发时间
  "iss": "lwx-crud"                    // 签发者标识
}
```

最终用户拿到的是一个单行字符串（约 200-400 字符），复制粘贴即可，不需要手动输入。

## 四、试用期机制

### 4.1 防频繁重装

纯本地「首次启动时间戳」方案，用户卸载重装就能无限白嫖。解决方式：**试用资格跟机器走，不跟安装走**。

试用记录双位置写入（读取时任意一个命中即可）：

| 存储位置 | Windows 路径 | 卸载时是否清理 |
|---------|------------|:---:|
| userData 目录 | `%APPDATA%/<appName>/trial.dat` | 通常不清理 |
| 注册表 | `HKCU\Software\<appName>\Trial` | 不清理 |

### 4.2 试用流程

```
应用启动
  │
  ├── 本地有正式授权文件？ ──→ 正常启动
  │
  ├── 没有授权文件
  │   │
  │   ├── 采集当前机器码
  │   ├── 扫描双位置，查找匹配当前机器码的试用记录
  │   │
  │   ├── 找到了 ──→ 检查是否过期
  │   │               │ 未过期 → 进入试用模式（显示剩余天数）
  │   │               │ 已过期 → 锁定，要求购买授权
  │   │
  │   └── 没找到（纯新机器）──→ 创建试用记录，双写入，进入试用
```

### 4.3 局限性

以下情况仍可绕过试用（需诚实面对）：

- 重装操作系统（所有痕迹清空）
- 虚拟机快照回滚
- 技术用户用 Process Monitor 追踪所有写入位置后逐一清理

但这类用户本就是少数，安全目标为"简单防一下"。

## 五、应用内组件设计

### 5.1 模块划分

```
src/main/license/
├── machine-id.ts        # 采集硬件信息，生成机器码
├── crypto.ts            # Ed25519 签名验证（使用 Node.js crypto）
├── license-store.ts     # 授权文件的读写 + 试用记录双写
├── license-validator.ts # 验证入口：签名校验 + 机器码匹配 + 过期检查
├── license-window.ts    # 激活窗口（BrowserWindow）
└── index.ts             # 统一导出 startupLicenseCheck()

src/renderer/src/views/
└── LicenseActivate.vue  # 激活界面组件

dev-tool/
└── generate-license.ts  # 开发者授权码生成工具（独立脚本，不入库）
```

### 5.2 启动流程

```
app.whenReady()
  → initFileTransport()
  → initDb()
  → registerUserController()
  → licenseCheck = checkLicenseOrTrial()
  → if licenseCheck === 'valid':
      createSplashWindow() → createWindow()   // 原流程
  → else:
      createLicenseWindow()                   // 显示激活窗口
      // 激活成功后 → 关闭激活窗口 → createSplashWindow() → createWindow()
      // 未激活退出 → app.quit()
```

### 5.3 激活窗口体验

- 首次启动自动弹出，不可跳过
- 展示机器码（文本 + 复制按钮）
- 授权码输入框 + 激活按钮
- 试用状态显示（剩余天数 + "继续试用"按钮）
- 过期提醒：到期前 7 天开始提示

## 六、安全保障层次

| 层级 | 措施 | 防御目标 |
|:---:|------|---------|
| L1 | Ed25519 非对称签名 | 杜绝伪造授权码 |
| L2 | 机器码模糊绑定 | 防止一个授权码在多台机器使用 |
| L3 | 公钥拆分拼接 | 防止直接搜索替换公钥 |
| L4 | 逻辑分散 | 提高 patch 门槛 |
| L5 | 授权文件签名校验 | 防篡改本地存储 |

桌面应用的离线授权没有绝对安全。目标是提高到「大多数人愿意付费」的程度。

## 八、总结

核心三要素：

1. **机器码** = 多硬件指纹 + 模糊匹配（≥3/4 维度）→ 绑定机器又有容错
2. **授权码** = Ed25519 签名（载荷 + 签名）→ 离线可验、无法伪造
3. **私钥** = 开发者独占，绝不离开发环境 → 安全根基

整个方案完全基于 Node.js 内置 `crypto` 模块，无需新增任何 npm 依赖。
